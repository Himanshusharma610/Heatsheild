## 1. Executive Summary & Safety Declarations

The **HeatShield Bharat Alert Management System** evaluates validated environmental readings against explicitly configured threshold rules to generate auditable, deterministic alert episodes for worksite decision support.

### Critical Safety Declarations
1. **Decision Support Only:**
   Alerts generated by this system are operational decision-support notifications intended for worksite supervisors and health/safety personnel. They **must not** be presented as medical diagnoses, predictions of individual heatstroke or thermal strain, or official government warnings.
2. **Provisional Development Thresholds:**
   No government-mandated or officially approved Indian occupational safety thresholds (e.g., from NDMA, MoHFW, or state heat action plans) have been officially codified into the software as legal mandates. Any default or test rules (such as Heat Index $\ge 41^\circ\text{C}$ for Warning or $\ge 54^\circ\text{C}$ for Critical) represent provisional development reference points. Formal production safety thresholds remain subject to institutional review and site-specific calibration.
3. **Hardware & Connectivity Boundaries:**
   Physical ESP32 microcontrollers and sensors remain unpurchased and unconfirmed. Backend alert evaluation, persistence, and deduplication occur exclusively upon telemetry ingestion over an active network connection. Backend alerts cannot be delivered during network partitions or power outages. Future local hardware alerts (LEDs, buzzers) on ESP32 firmware are distinct and require separate verification once physical units are procured.

## 2. Alert-Rule Schema & Validation

Alert rules define environmental criteria under which an alert episode is triggered. Rules can be configured globally (worksite-wide or fleet-wide) or targeted to a specific worksite or device.

### 2.1 Rule Data Model
| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `UUID` (PK) | Globally unique identifier for the rule. |
| `name` | `VARCHAR(100)` | Human-readable identifier (e.g., `extreme_heat_index_warning`). |
| `metric` | `VARCHAR(50)` | Environmental metric being evaluated (`temperature_c`, `relative_humidity_pct`, `heat_index_c`). |
| `operator` | `VARCHAR(10)` | Comparison operator (`gt`, `gte`, `lt`, `lte`, `eq`). |
| `threshold` | `NUMERIC(8,2)` | Finite threshold value in the metric's standard engineering units. |
| `severity` | `VARCHAR(20)` | Alert severity tier (`info`, `warning`, `critical`). |
| `worksite_id` | `UUID` (Nullable) | Optional foreign key scoping the rule to a specific worksite. |
| `device_id` | `UUID` (Nullable) | Optional foreign key scoping the rule to a specific hardware node. |
| `is_active` | `BOOLEAN` | Administrative toggle to enable or disable evaluation. |
| `version` | `INTEGER` | Rule version counter for auditability (starts at 1). |

### 2.2 Validation Invariants
Rules are strictly validated prior to persistence or evaluation via `validate_rule_parameters()`:
- **Supported Metrics:** Only `temperature_c`, `relative_humidity_pct`, and `heat_index_c` are admitted.
- **Supported Operators:** Only `gt` ($>$), `gte` ($\ge$), `lt` ($<$), `lte` ($\le$), and `eq` ($=$) are allowed.
- **Threshold Plausibility Bounds:**
  - `temperature_c`: $[-50.0^\circ\text{C}, 100.0^\circ\text{C}]$
  - `relative_humidity_pct`: $[0.0\%, 100.0\%]$
  - `heat_index_c`: $[20.0^\circ\text{C}, 80.0^\circ\text{C}]$
- **Non-Finite Reject:** `NaN`, `+Infinity`, and `-Infinity` are unconditionally rejected with HTTP 422.

## 3. Deterministic Alert Evaluation

Alert evaluation executes deterministically as part of telemetry ingestion pipeline or via on-demand evaluation:

```
Validated Sensor Reading + Active Rules
                │
                ▼
┌──────────────────────────────────────────────┐
│        Alert Engine: evaluate_rule()         │
│  - Check metric availability                 │
│  - Fail-safe check for missing/stale data    │
│  - Module 7 Heat Index integration           │
│  - Deterministic arithmetic comparison       │
└──────────────────────┬───────────────────────┘
                       │
         Condition met?│
         ┌─────────────┴─────────────┐
         ▼ No                        ▼ Yes
    [No Action]             Check Active Episode
                         (Deduplication Key Match)
                                     │
                     ┌───────────────┴───────────────┐
                     ▼ Episode exists                ▼ New Episode
               [Deduplicated]                 Insert Alert (status=triggered)
```

### 3.1 Fail-Safe Invariants
1. **Missing Data Never Assumed Safe:** If a metric value is `None` or absent from the reading, the rule evaluates to `False`. It **never** defaults to zero, low risk, or safe.
2. **Quality-Aware Filtering:** Readings flagged as `invalid`, `suspect`, or `extreme_temperature` do not trigger false heat-risk alerts.
3. **Stale Reading Rejection:** Heat index calculations returning `is_stale: true` or `status: "stale"` are rejected from evaluation.
4. **Immutability of Telemetry:** Evaluation never mutates or deletes the underlying `sensor_readings` record.

## 4. Deduplication Policy & Alert Episodes

To avoid flooding supervisors with hundreds of duplicate notifications during sustained heat events, the system enforces strict episode deduplication:

### 4.1 Deduplication Key Format
$$\text{key} = \text{device}:\{\text{device\_id}\}:\text{rule}:\{\text{rule\_id}\}$$

*(Or $\text{worksite}:\{\text{worksite\_id}\}:\text{rule}:\{\text{rule\_id}\}$ for worksite-level rules).*

### 4.2 Episode Lifecycle & State Machine
An active alert episode is defined as an alert matching the deduplication key where:
$$\text{status} \in \{\text{triggered}, \text{acknowledged}\}$$

```
                ┌──────────────┐
                │  Triggered   │◄──────────────┐
                └──────┬───────┘               │
                       │                       │
         Supervisor    │                       │ Condition
        Acknowledge    │                       │ re-occurs
                       ▼                       │
                ┌──────────────┐               │
                │ Acknowledged │               │
                └──────┬───────┘               │
                       │                       │
         Supervisor    │                       │
          Resolve      ▼                       │
                ┌──────────────┐               │
                │   Resolved   │───────────────┘
                └──────────────┘
                       ▲
                       │ Timeout / Invalidation
                ┌──────┴───────┐
                │   Expired    │
                └──────────────┘
```

- **During Active Episode (`triggered` or `acknowledged`):** Subsequent incoming readings that breach the threshold are deduplicated. No secondary alert rows are created.
- **After Episode Termination (`resolved` or `expired`):** The episode is closed. If a subsequent reading breaches the rule again in the future, the system treats this as a **genuinely new alert episode**, generating a new record with a new UUID and timestamp.

## 5. Supervisor Acknowledgement & Auditing

The system enforces separation between **device credentials** and **supervisor credentials**.

### 5.1 Authorization Invariants
- **Device Isolation:** Hardware devices transmitting via `X-Device-Token` are strictly forbidden from acknowledging alerts or managing rules (HTTP 401 Unauthorized).
- **Supervisor Role Required:** Acknowledgement (`/acknowledge`) and resolution (`/resolve`) require authenticated user credentials with role `supervisor` or `admin`.
- **Viewer Role Prohibited:** Read-only `viewer` accounts receive HTTP 403 Forbidden.

### 5.2 Audit Trail (`alert_acknowledgements`)
When a supervisor acknowledges an alert, an immutable record is created:
- `alert_id`: Target alert UUID.
- `user_id`: Authenticated supervisor UUID.
- `action_taken`: Documented safety mitigation (e.g., `"Provided mandatory 15-min hydration break and shade canopy."`).
- `notes`: Optional detailed observations.
- `acknowledged_at`: Precise ISO 8601 UTC timestamp.

### 5.3 Valid State Transitions
| Current Status | Target Status | Permitted? | Response |
| :--- | :--- | :--- | :--- |
| `triggered` | `acknowledged` | Yes | 200 OK |
| `acknowledged` | `acknowledged` | Yes (Update action) | 200 OK |
| `resolved` | `acknowledged` | **No** (Terminal) | 409 Conflict |
| `expired` | `acknowledged` | **No** (Terminal) | 409 Conflict |
| `triggered` | `resolved` | Yes | 200 OK |
| `acknowledged` | `resolved` | Yes | 200 OK |
| `resolved` | `resolved` | Yes (Idempotent) | 200 OK |

## 6. API Reference

All endpoints are mounted under `/api/v1` and return JSON.

### 6.1 List Alerts
- **Method:** `GET /api/v1/alerts`
- **Query Parameters:**
  - `status`: Optional filter (`triggered`, `acknowledged`, `resolved`, `expired`).
  - `severity`: Optional filter (`info`, `warning`, `critical`).
  - `worksite_id`: Optional UUID filter.
  - `device_id`: Optional UUID filter.
  - `page`: Page number (default: 1).
  - `page_size`: Limit per page (default: 20, max: 100).
- **Response `200 OK`:**
```json
{
  "items": [
    {
      "id": "e0a1b2c3-d4e5-4f6a-8b9c-0d1e2f3a4b5c",
      "rule_id": "c7a8b9d0-1234-5678-9abc-def012345678",
      "device_id": "a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d",
      "worksite_id": "b2c3d4e5-f6a7-8b9c-0d1e-2f3a4b5c6d7e",
      "severity": "critical",
      "status": "triggered",
      "trigger_value": 42.50,
      "trigger_condition": "heat_index_c >= 41.00",
      "rule_version": 1,
      "triggered_at": "2026-10-25T10:15:00Z",
      "acknowledged_at": null,
      "acknowledged_by": null,
      "resolved_at": null
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 20,
  "pages": 1
}
```

### 6.2 Acknowledge Alert
- **Method:** `POST /api/v1/alerts/{alert_id}/acknowledge`
- **Headers:** `X-User-Id: <supervisor_uuid>`
- **Request Body:**
```json
{
  "action_taken": "Provided hydration and moved outdoor crew to ventilated break tent.",
  "notes": "Ambient heat index reached 42.5 C at Dock 4."
}
```
- **Response `200 OK`:**
```json
{
  "id": "e0a1b2c3-d4e5-4f6a-8b9c-0d1e2f3a4b5c",
  "status": "acknowledged",
  "acknowledged_at": "2026-10-25T10:20:00Z",
  "acknowledged_by": "00000000-0000-0000-0000-000000000001",
  "action_taken": "Provided hydration and moved outdoor crew to ventilated break tent.",
  "message": "Alert acknowledged successfully."
}
```

### 6.3 Resolve Alert
- **Method:** `POST /api/v1/alerts/{alert_id}/resolve`
- **Headers:** `X-User-Id: <supervisor_uuid>`
- **Request Body:**
```json
{
  "resolution_notes": "Heat index returned below 38.0 C; shift concluded safely."
}
```
- **Response `200 OK`:**
```json
{
  "id": "e0a1b2c3-d4e5-4f6a-8b9c-0d1e2f3a4b5c",
  "status": "resolved",
  "resolved_at": "2026-10-25T11:00:00Z",
  "message": "Alert resolved successfully."
}
```

### 6.4 List Alert Rules
- **Method:** `GET /api/v1/alert-rules`
- **Query Parameters:** `metric`, `severity`, `is_active`, `page`, `page_size`.

### 6.5 Create Alert Rule
- **Method:** `POST /api/v1/alert-rules`
- **Headers:** `X-User-Id: <supervisor_or_admin_uuid>`
- **Request Body:**
```json
{
  "name": "high_ambient_temperature_warning",
  "metric": "temperature_c",
  "operator": "gte",
  "threshold": 38.0,
  "severity": "warning",
  "worksite_id": null,
  "device_id": null,
  "is_active": true
}
```

## 7. Automated Test Coverage

The alert engine and lifecycle endpoints are covered by comprehensive automated tests in [`backend/tests/test_alert_engine.py`](file:///home/himanshu/projects/heat%20shield/backend/tests/test_alert_engine.py):

1. **Unit Tests — Evaluation Logic:**
   - Valid rule matches reading when condition is satisfied.
   - Non-matching condition evaluates to false without alert creation.
   - Disabled rules (`is_active=False`) are excluded from evaluation.
   - Missing or non-finite readings do not trigger false alerts.
   - Unsupported metrics, operators, or non-finite thresholds are rejected.
2. **Persistence & Lifecycle Transitions:**
   - Alerts are persisted atomically to PostgreSQL/SQLite repository layer.
   - Repeated evaluations during an active episode are deduplicated.
   - After resolution, subsequent breaches trigger a new alert episode.
   - Valid lifecycle state transitions: `triggered` $\to$ `acknowledged` $\to$ `resolved`.
   - Invalid transitions (e.g., acknowledging an already resolved or expired alert) return HTTP 409 Conflict.
3. **Authorization & Access Control:**
   - Device tokens (`X-Device-Token`) are rejected on supervisor endpoints.
   - Viewer role is rejected with HTTP 403.
   - Unauthenticated requests receive HTTP 401.
4. **End-to-End Pipeline Integration:**
   - Authenticated telemetry ingestion (`POST /api/v1/readings`) automatically triggers alert evaluation and persists active alerts in the same transaction.
